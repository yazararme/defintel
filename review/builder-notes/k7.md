## Schedule impact

A run waits only for an earlier run of the **same workflow on the same ref**.

- **collect-news:** there are 2 runs a day (05:01 and the ~11:00 backstop), about 5.5 h apart, and each lasts at most 19 min. They never wait for each other. Before K7 they could queue behind pull-drive. That no longer happens.
- **pull-drive:** runs last ≤1.7 min, and the crons are at least 10 min apart. A wait needs a run that lasts more than 10 min. The only step that can take that long is the notify loop (up to 60×10 s + 20 s ≈ 10.5 min, and only when Pages is slow). The worst case is then a few minutes of queueing for the next run, which would find no new report anyway. The 06:16 publish never waits: nothing else in the pull-drive group runs at that time. Before K7 it could have waited up to 19 min behind a collect-news run. It no longer can.
- **missing-report:** one ~6 s run a day, so it never waits.
- **build:** a build waits only behind a build of the same ref (≤2.1 min). This is what the K7-1 evidence expects: the second back-to-back dispatch shows Pending/Queued, then runs.

The 05:01 dispatch, the ~11:00 backstop and the 06:16 publish all run exactly as before.

## GitHub limit: 1 running + 1 pending per group

A third arrival cancels the pending run. `cancel-in-progress: false` does not prevent this. Can it happen in the real schedule?

- **collect-news:** no. It has at most 2 runs a day, hours apart.
- **missing-report:** no. It runs once a day.
- **pull-drive:** only in theory. It would need a run lasting more than 20 min (two cron slots), and the observed max is 1.7 min, with a hard cap of ~12 min set by the notify loop. Even if it happened, the dropped pending run is a duplicate of the newer one, which still runs and pulls the same Drive state. No report is lost.
- **build:** only if a person pushes 3+ times to one ref within ~2 min, or dispatches 3 times back to back. The middle run is then cancelled and the newest commit is still built. The orchestrator's K7 evidence uses exactly **two** dispatches, so it is not affected. A third dispatch would cancel the second, and K7-1 requires no cancellations.

## Cross-workflow risk from removing the shared `publish` group

collect-news and pull-drive now run in different groups, so GitHub no longer keeps them apart. No overlap between them has been observed since 18 Sep: the smallest gap between a collect run and a pull-drive run was 17 min. GitHub's late cron firing is unpredictable, though, so an overlap cannot be ruled out.

**1. Concurrent push race to main: YES, possible (low likelihood).**
Both workflows commit, then run `git pull --rebase --autostash origin main`, then `git push`. That shrinks the race but does not remove it. If the other workflow pushes between this one's pull and push, the push is rejected (non-fast-forward) and the step fails, with no retry. There is a second failure mode. Both workflows run `build.py`, which regenerates the same `data/*.json` and site HTML, so if both run on overlapping inputs the rebase can conflict on generated files. In pull-drive this fails the `publish` step: the report and notification are delayed until the next pull-drive run, which starts from a fresh checkout and succeeds. The report is late but not lost. (build.yml on main pushes without `pull --rebase`, but only on human pushes, and it was never in the `publish` group, so that part is unchanged.)

**2. Duplicate daily issue: YES, possible (low likelihood).**
`scripts/uyari.py gonder()` does an unlocked check-then-act. `_issue_bul()` lists issues, and if it finds none, the script `POST`s a new one. If collect-news and pull-drive both reach their final "Operatör uyarıları" step on main at nearly the same time, and both have warnings, each can see no issue and each can open `DEFINTEL uyarıları · <gün>`. The same unlocked read-modify-write applies to the `PATCH` of an existing issue body, so one run's appended lines can be lost. The window is only the few seconds of that last step, and it needs warnings from both runs. Per-workflow groups do fix the same-workflow case, which is the one K7-2 tests (two builds → one issue). No change was made for the cross-workflow case, as the brief asked.
